# Scenario DSL 设计原则

> 可比性是唯一的表达力轴；控制流是声明，不是判定。

x-agent-suite 当前的 `ScenarioSpec` 是极简形态（`prompts[]` + `expected`）。当 DSL 扩展时，以下原则用来裁决「某个能力该不该进框架」。

## 可比性轴

问的不是「语法复杂不复杂」，而是：**这项能力会不会让两个被测系统考不同的卷子？**

| 能力                                             | 毁可比性？                               | 裁决            |
| ------------------------------------------------ | ---------------------------------------- | --------------- |
| 静态 prompt 列表 + 逐轮断言 + 会话终态断言       | 否                                       | ✅ 基线         |
| 世界操作（改 workspace / 等待 / 断言 / 重启）    | 否——每个系统按同一顺序经历同一批操作     | ✅ 可做         |
| 控制键与非文本片段                               | 否                                       | ✅ 可做         |
| 变量插值 / 参数化                                | 否——展开在跑之前完成，每个系统拿到的一样 | ✅ 宿主语言层做 |
| 主动分支：为探索被测系统而故意走不同路径         | **会**                                   | ❌ 明确不做     |
| 被动分歧处理：脚本想要同一件事，但被测系统没配合 | 不必然——取决于处理方式                   | ✅ 必须处理     |

**主动分支不做。** 系统 A 走 `when`、系统 B 走 `else`，两条轨迹轮数不同、触发的判据集合不同、判据基数不同——矩阵对比当场失去意义。自适应探针有价值，但那是**调试工具**不是**回归矩阵**，将来另开非矩阵入口，不进 DSL。

## 为什么必须有逐轮断言

会话级判据把两种完全不同的失败压成同一个结果：

- **行为从未发生** —— 能力缺失
- **行为发生过，但几轮之后衰减了** —— 上下文被挤出、注意力丢失

后者在长会话里往往更常见。逐轮断言让「第 1 轮生效」和「第 7 轮才生效」拿到不同的分数。

## 分歧点：断言 + 固定纠偏 + LLM 分类器

被测对象是 AI——它可能反问、拒答、先干别的。此时后续每轮的判据仍在给一个场景作者从未设想的状态打分。**分歧处理不是「可玩性」，是「结果有效性」。**

| 处理方式                                         | 形态                             | 可比性代价                       | 裁决        |
| ------------------------------------------------ | -------------------------------- | -------------------------------- | ----------- |
| 转向——切到另一串轮次                             | 真分支                           | 高，等于主动分支                 | ❌ 不做     |
| 断言——判为「前提不成立」，停掉后续轮次           | 轮级 `precondition`              | **零**（但这次运行降为 no-data） | ✅          |
| 固定纠偏——送一句**声明好的**固定内容把它拽回主线 | `onDivergence.recover[]`（静态） | 低，须在报告里留痕               | ✅          |
| LLM 决策——让模型决定下一步                       | 分类器 or router                 | 见下                             | ✅ 仅分类器 |

### LLM 可以当分类器，不能当控制器

| 角色                  | 抖动表现为                       | 能不能兜住               |
| --------------------- | -------------------------------- | ------------------------ |
| judge（判 pass/fail） | 分数方差                         | 能。可重复采样、算一致率 |
| router（决定下一步）  | **送了哪些轮、跑了哪些判据**变了 | **不能。分母变了。**     |

router 抖动之下，同一系统跑两次不是同一个实验。因此：

```text
LLM 允许当分类器：产出「这次发生了哪类分歧」的标签 + 证据 → 落在判据里
LLM 不允许当控制器：标签到动作的映射必须是场景里声明好的静态表
```

**分类是 AI，反应是一张表。** 控制流始终可审计、可复现。

## `expect` 键必须做引用完整性校验

「框架不认识 criterion 名」有一个危险的推论。设想 `expect: { groundng: true }`（少一个 i）：

```text
没有同名 criterion → 这一轮不跑任何判据 → 场景绿了
```

这是评估工具最坏的失效模式：**假绿**。loader 必须在加载期把每个 `expect` 键与已注册 criterion 名做交叉校验，未注册即报错。这是纯引用完整性检查，零领域词汇。

## 参数化不需要模板语法

「同一个场景换 7 个输入」不需要 `{{ }}`、不需要 `Examples` 表。因为 scenario 的契约面是对象，**宿主语言就是模板层**：

```ts
const cases = ["短查询", "跨文档查询", "不存在的实体"];
export const scenarios = cases.map((q, i) =>
  makeScenario(`retrieval/case-${i}`, q),
);
```

展开在跑之前完成，每个被测系统拿到的展开结果完全一致，**可比性零代价**。

## 衰减看得见，也要断言得了

同一 criterion 在多个轮次上重复声明，报告就能打印衰减点：

```ts
prompts: [
  '第一个问题',
  '追问细节',
  '再追问',
],
expected: {
  // 第 0 轮与第 2 轮分别判
}
```

如果想把「不许衰减」做成门禁——比如「后三轮至少两轮 pass」——需要框架提供「序列级 criterion」，把某 criterion 的逐轮 `{ pass, score }` 按序交给 consumer 的 criterion 去判阈值。阈值属于领域，留在 consumer。
