# 边界纪律

> 分层腐化是常态，设计目标是**可见**与**可回收**。

x-agent-suite 被多个 consumer 共同依赖。若不守边界，结果不是「框架变脏」，而是**每个 consumer 各自腐化、各自回收，付 N 次，且 N 次互不复用**。

守住边界，这笔必然要付的成本被收拢到一处付一次——回收的对象是一个有明确契约的包，不是 N 份纠缠的应用代码。

## 前提：腐化不可避免

开发过程中，为了满足需求，分层会被自然地强行融合。到时候为了解决问题，再倒过来做强行分层——**这件事不可避免。**

所以 x-agent-suite 的设计目标不是「防止腐化」，而是：

1. 腐化发生时**当天可见**，而不是半年后考古。
2. 腐化**局部化**在可枚举的少数几个点上。
3. 回收时面对的是一份 **grep 就能列全的清单**，不是一次全代码库排查。

下面四条守卫是**腐化检测器**，不是防火墙。它们拦不住需求压力，只保证压力穿透时留下痕迹。

## 一个真实的破口案例

某 consumer 的通用层里，有个文件叫 `assertions/observation.mjs`，住在一个从第一天就命名为 `core`、README 写着「多种 carrier 均由此扩张」的包内。它的实际内容：

```js
export function xkbCommands(commands) {
  /* 硬编码某个 CLI 名的正则 */
}
if (observation.carrier !== "pi") {
  /* 硬编码某个具体 carrier */
}
observation.metadata?.xKbPluginInjection; // 硬编码某个领域字段名
```

**这证明了：起一个通用的名字、写一句通用的 README、靠开发者纪律，都挡不住融合。**

更重要的是它的成因——`guardFailure()` 需要表达「某插件未注入导致场景前提不成立」这个失败类别，而通用层**没有提供领域自定义失败类别的口子**。开发者急着让判据可用，只能硬编码进去。

**这是缺口设计问题，不是纪律问题。** 骂纪律没用，下次还会发生。

## 四条守卫

| #   | 守卫         | 实现                                                                  | 作用                     |
| --- | ------------ | --------------------------------------------------------------------- | ------------------------ |
| G1  | 依赖方向单向 | 独立仓库，`package.json` 永不依赖任何 consumer                        | 物理保证，白拿           |
| G2  | 词汇表检查   | `pnpm boundary` 扫 `packages/*/src/**` 领域词，命中即 fail            | 腐化当天可见             |
| G3  | 自举测试     | `packages/*/tests/` 在无任何 consumer、无领域环境变量的机器上必须全绿 | 「通用性」的可执行定义   |
| G4  | 零内建判据   | 框架不预置任何具体 criterion / scenario / driver profile              | 判据是领域词汇最大的载体 |

**G4 是最容易破的一条。** 写着写着一定会冒出「路由命中挺通用的吧，别的系统也有路由概念」这种念头。不要。一条内建判据会带进一整套领域词汇，G2 和 G3 会跟着一起崩。

**G3 是最硬的一条。** 哪天测试跑不起来需要装某个被测系统，说明污染已经发生，此时先修边界再谈别的。

## 三个合法出口

真正杀死分层的，是**需求压力没有合法出口**。有出口，开发者手边就有一个不用凿墙的选项。

### 出口一：metadata 自由区

`Observation`、`SessionObservation`、`DriverOpenContext`、`ScenarioSpec`、`HarnessProfile` 上都有 `metadata: Record<string, unknown>`。框架只透传，不解释任何键。

上文那个 `xKbPluginInjection` 本来就该活在这里。

### 出口二：失败类别注册

框架内建的失败类别只有四条，全部与领域无关：

| 前缀         | 含义                              |
| ------------ | --------------------------------- |
| `payload`    | driver 未返回可解析的 Observation |
| `driver-env` | driver 启动或环境准备失败         |
| `timeout`    | 会话或单轮等待超时被中断          |
| `config`     | 场景声明缺失，判据无法判定        |

领域自有的类别（如「某插件未注入，场景前提不成立」）自行注册前缀。框架只做分类统计，不认识语义。

### 出口三：插件注册表

driver、`HarnessProfile`、判据、scenario 全部通过注册进入，框架源码内不枚举取值。想加一个 CLI、一个判据、一种 driver 形态，都不需要改框架源码。

## 边界债务留痕

确实必须穿透边界时——会有这种时候，不必假装不会——留一行标记：

```ts
// BOUNDARY-DEBT(<consumer>): 为什么必须穿透、什么条件下可以回收
```

`pnpm boundary` 统计条数并列出位置。行尾标记只豁免本行；独占一行的标记只豁免下一非空行。推荐独占形式，避免格式器拆分长行后使标记与目标代码脱离。

**债务允许存在，但必须可枚举。** 这比「一次设计对、永不腐化」现实得多：接受「每隔一段时间做一次边界回收」是常态，而回收成本靠这份清单压到最低。

## 回收约定

- 每次契约变更（`packages/contracts/src/` 改动）时顺带看一眼债务清单。
- 债务条数超过 10 条时，`pnpm boundary` 提示回收，但不阻断。
- 回收的判断标准只有一条：**这条债务是否能改用三个合法出口之一表达？** 能就改，不能就留着并更新注释里的回收条件。
