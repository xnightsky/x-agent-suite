# Agent 消息通信的两层拆分

> 把 Agent 之间的消息通信拆成**传输层**与**入站触达层**，两层职责正交、独立演进。
>
> 这是一份跨项目的架构观察，不是 x-agent-suite 自身的机制规格。
> 关联：
>
> - [mcp-push-vs-pull.md](./mcp-push-vs-pull.md)（宿主分级表的一手证据）
> - [../notes/kimi.md](../notes/kimi.md)（Kimi 空闲点火与双 TUI 互通实测）

## 1. 两层定义

| 层                  | 职责                                                        | 落点                                         | 例子                                                              |
| ------------------- | ----------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------- |
| **L1 · 消息传输层** | 寻址、路由、持久化、至少一次送达、拉取/确认消费语义         | broker / wire 协议 / SDK / MCP facade        | 会话注册、inbox、pull/ack、ask/reply/cancel/presence              |
| **L2 · 入站触达层** | 把已落 inbox 的消息**送进模型上下文**、按需**唤醒空闲会话** | 各 Agent 宿主（CLI/TUI/IDE）的扩展/插件/hook | Claude Code inbox socket、Kimi `Stop` block、Codex app-server RPC |

两条不可商量的边界：

1. **L1 不知道宿主是谁。** 传输层不出现任何具体 Agent / CLI / IDE 的名字；L2 要的一切能力（pull、ack、pending、presence）都是宿主中立的协议原语。
2. **L2 不重新发明传输。** 宿主侧不实现自己的路由、寻址、持久队列；消息一律经 L1 的通用原语进出，L2 只做「最后一公里」的模型注入与唤醒。

## 2. 为什么必须分层

不分层的失败模式有两种，在真实 CLI 上都已验证：

- **指望协议层 push 进模型**：标准 MCP notification 被 host 当控制面信号（刷工具列表、显示日志），模型永远不知道有新消息。Kimi Code 已实测双通道（ACP + TUI）均不注入；Claude Code 除私有 channels 外同样不注入。
- **在传输层里塞宿主逻辑**：核心层若要知道「怎么叫醒 pi / Claude / Codex」，每加一个宿主就污染一次通用协议，最终协议变成宿主特性的缝合怪。

分层后两层的质量属性解耦：L1 对**持久性、去重、顺序**负责；L2 对**实时性、模型可见性**负责。一端掉链子时故障域清晰——消息落盘了但模型没反应是 L2 的事，消息没到 inbox 是 L1 的事。

## 3. L1 向 L2 暴露的接口

L1 只需暴露宿主中立的原语，L2 在此基础上做注入：

| 原语       | 语义                                           |
| ---------- | ---------------------------------------------- |
| 发送消息   | 给对端 session / inbox 投递一条消息            |
| 拉取 inbox | L2 按需要主动拉取未读消息                      |
| 确认消费   | L2 注入成功后显式 ack，完成 at-least-once 语义 |
| 查询状态   | 在线会话列表、presence、pending ask 等         |

**L1 不保证模型已看到消息。**「已送达 inbox」与「已进入模型上下文」是两个独立事实，后者不归 L1 管。

## 4. L2 按宿主官方通路分级

不同宿主把消息送进模型的能力差异极大。下表基于一手实测或官方文档：

| 宿主        | 官方入站通路                                                                                              | 空闲唤醒                         | 评级     |
| ----------- | --------------------------------------------------------------------------------------------------------- | -------------------------------- | -------- |
| pi          | 扩展 API `sendUserMessage`（steer/followUp）                                                              | ✅                               | 最强     |
| Claude Code | v2.1.224 跨会话 inbox socket；hooks `async`+`asyncRewake` 兜底                                            | ✅                               | 官方支持 |
| Codex       | app-server JSON-RPC：`turn/start` / `turn/steer` / `thread/inject_items` / `thread/queue/add`；hooks 兜底 | ✅（与 TUI 共存未验证）          | 强       |
| Kimi Code   | TUI：`Stop` block 续轮捎带 + `UserPromptSubmit` 空闲期下一轮兜底；托管：`kimi web` REST 外部点火          | 托管 ✅；TUI ❌（仅续轮/下一轮） | 中       |
| Gemini CLI  | hooks 同步注入上下文（BeforeAgent/SessionStart）                                                          | ❌                               | 弱       |
| Cursor      | stop hook `followup_message`                                                                              | ❌（仅续轮）                     | 弱       |
| Windsurf    | hooks 无注入字段                                                                                          | ❌                               | 最弱     |

**L2 的实现约束**：

1. 注入通路**只用宿主官方机制**（扩展 API / 官方 IPC / hooks），不依赖私有逆向通道；
2. 消费顺序：**先注入成功，再 ack**；注入失败不 ack，消息留在 inbox 等下次拉取，保证 at-least-once 不在最后一公里断掉；
3. L2 可以退化：宿主没有唤醒能力时，最小可用形态 = 后台事件监听落 inbox + 前台 hook 自然边界单次检查；
4. 禁止把轮询塞进普通 AI 前台 turn。

## 5. 层间故障语义

| 现象                             | 故障域              | 对外表述                             |
| -------------------------------- | ------------------- | ------------------------------------ |
| 消息未落对端 inbox               | L1                  | 传输失败                             |
| 已落 inbox、模型无反应           | L2                  | 触达缺失（宿主能力短板或壳仓未实现） |
| 已落 inbox、模型看到、但重复看到 | L2 注入成功但未 ack | 消费语义断裂                         |
| 传输层重启后消息仍在             | L1 正常             | 持久 inbox 按设计工作                |

## 6. 不变量

1. L1 任何模块不出现具体宿主名；宿主识别只能以 L2 注入的 metadata（名称、cwd、model 等展示字段）形式存在，且不被信任。
2. L2 不得绕过 L1 直连另一会话的私有状态做写入；只读旁路允许，写入必须经 L1 原语。
3. 任何 notification / event 在未逐宿主验证前，不得宣称「模型会收到」。
4. 新增宿主的成本约束：L1 零改动，全部工作落在该宿主壳仓的 L2 适配。若某宿主需求会改动 L1，先回到本文档复议边界。

## 7. 可宣称能力口径

| 组合                                 | 可宣称                                                  | 不得宣称                     |
| ------------------------------------ | ------------------------------------------------------- | ---------------------------- |
| 仅 L1                                | 任意宿主可双向收发（模型主动 pull/ack）                 | 实时推送、自动唤醒           |
| L1 + 强 L2（pi/Claude/Codex）        | 消息实时进模型上下文、可唤醒空闲会话                    | 跨机、认证                   |
| L1 + 短板 L2（Kimi TUI）             | Stop 活跃轮续轮 + UserPromptSubmit 下一轮兜底（无轮询） | 空闲会话即时唤醒             |
| L1 + 托管 L2（Kimi server/ACP）      | 外部点火空闲会话                                        | TUI 会话同等待遇；API 稳定性 |
| L1 + 无 L2（Gemini/Cursor/Windsurf） | 经 facade pull 可用                                     | 任何实时性                   |
